## 一、需求拆解

| 能力 | 具体要求 | 技术难点 |
|---|---|---|
| 查到 | 输入中文名/日文名/拼音，匹配到唯一一部番 | 中文番名没有稳定的公开 API |
| 记住 | 状态、评分、看完日期、集数进度、短评 | 表结构问题 |
| 存素材 | 封面、截图、视频（引用或归档） | 体积大、要能拖动播放、要能截帧 |
| 找得到 | 封面墙、筛选、年度统计 | 索引与缩略图 |
| 多端 | 电脑上记，手机上看 | 桌面 App 与手机浏览器是两个世界 |

一条贯穿全局的判断：**这本质上不是"追番管理工具"，而是一个私有素材库**。素材不可再生、体积大，所以「数据在本地、不上传、可一键备份」是硬约束。

## 二、数据源实测（2026-11-23，本机网络）

| 数据源 | 用途 | 实测 |
|---|---|---|
| `api.bgm.tv`（Bangumi） | 中文元数据最全 | **不可达**，HTTP 000；`bgm.tv` 主站同样不可达 |
| `api.jikan.moe`（MAL） | 日文/英文元数据 | **不可达**，HTTP 000 |
| `api.themoviedb.org` | 海报 + 元数据 | **不可达**，HTTP 000 |
| `graphql.anilist.co` | 元数据 + 高清封面 | **可用** |
| `s4.anilist.co` | 封面图 CDN | **可用**，单张 83 KB |
| `unpkg.com/bangumi-data` | 中文标题离线数据集 | **可用**，8 MB / 8931 部 / 8403 部有简体中文名 / 8331 部带 AniList ID |

由此定下最核心的一条设计：

> **不把"搜番"押在任何在线 API 上。中文标题走本地离线索引，元数据和封面走 AniList 按需补全。**

两个实测细节决定了用法：
1. AniList 能识别中文（搜"进击的巨人"命中 id 16498），但**返回里没有中文字段**，只有 romaji / native / english，且限流约 30 次/分钟 —— 适合"补全"，不适合"搜索"。
2. `bangumi-data` 正好是桥梁：`title`（日文原名）+ `titleTranslate["zh-Hans"]`（中文名）+ `sites[]` 给出 Bangumi / AniList / MAL / TMDB 的 ID。拿到 AniList ID 就能顺着取封面。

## 三、形态决策：单进程内嵌服务 + 两个入口

你选了桌面 App，同时又要手机能看 —— 这两件事不能靠"打包一个 App"同时满足：手机装不了 Windows 桌面程序。

所以结构必须是：

```
桌面 Tauri 窗口 (WebView)  ─┐
                            ├─→  同一个 HTTP 服务  →  data/ + AniList
手机浏览器 (同一 Wi-Fi)     ─┘
```

桌面端的 WebView 不直接读文件，而是**加载本机服务**（`http://127.0.0.1:8787`）；手机访问 `http://<内网IP>:8787`。一套前端、一套接口、一套数据，桌面和手机吃到的是同一份。

### 为什么服务写在 Rust 里，而不是塞个 Node

| 做法 | 结果 |
|---|---|
| Tauri + Node sidecar（Hono 打包成 exe） | 业务代码全是 TS，改起来快；但要多带 50 MB Node 运行时，Windows 上 sidecar 打包/路径问题多，`pkg` 已停止维护 |
| **Tauri + Rust 内嵌 axum（选定）** | **安装包约 10 MB、装完约 20 MB，无运行时依赖，手机和桌面共用同一端口**；代价是首次 `cargo build` 慢（5–10 分钟），之后增量很快 |
| Tauri + 前端直连 SQLite | 桌面端能用，但手机没有这条路，等于维护两套逻辑 |

后端需要的每件事在 Rust 生态里都是现成的：`axum` 路由、`tower-http` 的 `ServeFile` 自带 Range（视频拖动就靠它）、`axum::extract::Multipart` 流式上传、`rusqlite`（bundled，免装 SQLite）、`image` 生成缩略图、`zip` 导出备份、`reqwest` 请求 AniList、`qrcode` 生成配对码。

### 搜索放在前端

8931 条标题不值得占服务端资源。把数据集预构建成**精简索引（约 1.5 MB，只留中文名/日文名/年份/AniList ID）打进安装包**，首次启动即可用、断网也能搜：

- 前端 `MiniSearch` 建索引，命中 <10 ms
- `pinyin-pro` 支持 `jjdr` → 进击的巨人
- 索引缓存在 IndexedDB，手机端首次进入下载一次后离线可用

服务端因此只负责三件事：**元数据补全、媒体流、数据库读写**。职责很薄，也就不用为搜索写第二套实现。

### 技术栈定稿

- 外壳：Tauri 2（WebView2）
- 后端：Rust + axum + tokio + rusqlite(bundled) + tower-http + reqwest + image + zip + qrcode
- 前端：React 19 + TypeScript + Vite + Tailwind + MiniSearch + pinyin-pro + TanStack Query
- 数据：单个 `data/` 目录，整体可拷可备份

## 四、数据模型

```sql
CREATE TABLE works (
  id             INTEGER PRIMARY KEY,
  anilist_id     INTEGER UNIQUE,
  bangumi_id     INTEGER,
  title_cn       TEXT NOT NULL,
  title_jp       TEXT,
  title_en       TEXT,
  aliases        TEXT,                    -- JSON 数组，手动补的别名/俗称
  year           INTEGER,
  format         TEXT,                    -- TV / MOVIE / OVA / WEB
  episodes_total INTEGER,
  cover_path     TEXT,                    -- 本地封面相对路径，不存外链
  synopsis       TEXT,
  genres         TEXT,
  status         TEXT DEFAULT 'plan',     -- plan/watching/done/paused/dropped
  rating         INTEGER,                 -- 1-10，0 = 未评
  progress       INTEGER DEFAULT 0,
  favorite       INTEGER DEFAULT 0,
  finished_at    TEXT,
  note           TEXT,
  media_mode     TEXT DEFAULT 'ref',      -- 这部番的默认存法：ref / archive
  created_at     TEXT DEFAULT (datetime('now'))
);

CREATE TABLE media (
  id          INTEGER PRIMARY KEY,
  work_id     INTEGER NOT NULL REFERENCES works(id) ON DELETE CASCADE,
  episode     INTEGER,
  kind        TEXT NOT NULL,              -- image / video
  storage     TEXT NOT NULL,              -- ref = 只记路径；archive = 已复制进库
  path        TEXT NOT NULL,              -- archive: 相对 data；ref: 绝对路径
  poster      TEXT,
  bytes       INTEGER,
  width       INTEGER, height INTEGER,
  duration    REAL,
  caption     TEXT,
  stamp       REAL,                       -- 截图对应视频时间点（秒）
  missing     INTEGER DEFAULT 0,          -- 引用模式下原文件已丢失
  created_at  TEXT DEFAULT (datetime('now'))
);

CREATE TABLE tags (id INTEGER PRIMARY KEY, name TEXT UNIQUE);
CREATE TABLE work_tags (work_id INTEGER, tag_id INTEGER, PRIMARY KEY (work_id, tag_id));
CREATE TABLE collections (id INTEGER PRIMARY KEY, name TEXT, cover_media_id INTEGER);
CREATE TABLE collection_items (collection_id INTEGER, work_id INTEGER, sort INTEGER,
                               PRIMARY KEY (collection_id, work_id));
```

存储模式的关键结论：**两种模式在播放上体验一致**。因为播放永远走 `/api/media/:id/stream`，由服务端读文件再流式吐给前端 —— 引用模式下手机也能播，不要求手机能访问那个路径。这一点必须在 P0 就设计好，否则后面改成代理会很痛。

引用模式的三个必要保护：
1. `path` 只接受白名单根目录下的绝对路径，防目录穿越
2. 每次列素材时 `stat` 一次，文件没了就标 `missing`，界面显示"原文件已移动，重新指定"
3. 引用模式不参与"打包备份"的完整性承诺，导出时明确列出有哪些素材没进包

## 五、核心流程

### 1. 搜索入库（两段式）

```
输入 → 归一化(去空格/全半角/繁简) → MiniSearch 前缀+模糊 → 候选卡片(中文名/日文名/年份)
     → 选中 → 按 anilistId 请求 AniList → 封面下载到 data/covers/ → 写入 works
```

第一段纯本地，断网可用；第二段联网补全。AniList 挂了也能先入库，信息以后补。

### 2. 素材写入

- 入口：拖拽 / **Ctrl+V 粘贴**（系统截图直接粘，最高频）/ 选择文件 / 手机相册
- 入库时可选「引用」或「归档到这」，默认跟随该番的 `media_mode`
- 服务端流式落盘，不经内存缓冲
- 图片生成 400px 缩略图；视频用 `<canvas>` 抓首帧做 poster —— **不需要 ffmpeg**
- 手机上传前先在 canvas 压到长边 2048 / q0.9，避免几 MB 原图走 Wi-Fi

### 3. 视频截帧

```js
canvas.getContext('2d').drawImage(video, 0, 0, w, h)
canvas.toBlob(b => upload(b), 'image/jpeg', 0.92)
```

同源本地文件，canvas 不会被污染。截图记 `stamp`，以后可一键跳回原片那一秒。

### 4. 手机配对

桌面端「连接手机」弹二维码，内容是 `http://192.168.x.x:8787/?t=<一次性口令>`。手机扫码进入后口令换 HttpOnly cookie，之后免输。

三个必踩的坑，提前写明：
- **Windows 防火墙**首次会弹窗，必须允许"专用网络"，否则手机打不开
- 电脑睡眠/关机则手机不可用，这是本地方案的固有限制
- Safari 不支持 HEVC 视频，播放前先探测 `canPlayType`，不支持就提示"该格式手机无法播放，建议用 H.264/WebM"

### 5. 备份

导出 zip：SQLite 快照 + `covers/` + `media/` 中 `storage='archive'` 的部分 + 一份 `manifest.json`（列出所有 ref 素材的原路径）。恢复走反向导入。

## 附录：体积与空间占用

### 程序本体

| 项 | 估算 | 说明 |
|---|---|---|
| 安装包（msi/exe） | **约 8–12 MB** | 压缩后；LZMA |
| 装完占磁盘 | **约 18–22 MB** | exe + 资源 + 内置索引 |
| 其中内置标题索引 | 1.5 MB | 不打这个包就每次联网拉 8 MB，不划算 |

小的原因很简单：Tauri 用系统自带的 WebView2（Win10 1803 以上都有），不分发 Chromium。同样功能的 Electron 版起步就是 120–150 MB。

主要占用来自依赖：axum + tokio 约 3 MB，reqwest/rustls 约 3 MB，rusqlite(bundled) 约 1.5 MB，image 约 2 MB。

### 数据占用（这才是真正会涨的部分）

| 内容 | 单份大小 | 常见量级 |
|---|---|---|
| 封面 | 80–400 KB（AniList 大图，平均约 200 KB） | 500 部 ≈ 100 MB |
| 截图 | 1080p JPEG 约 300–600 KB | 1000 张 ≈ 400 MB |
| 视频（归档模式） | 1080p H.264，24 分钟 ≈ 350–500 MB/集 | 一部 12 集 ≈ 5 GB |
| 视频（引用模式） | 0 | — |
| SQLite | 500 部 + 2000 条素材 ≈ 2–3 MB | 可忽略 |

三种使用强度的实际占用：

- **只记番 + 存封面**：500 部 ≈ 0.1 GB
- **加截图**：1000 张 ≈ 0.5 GB，仍然无压力
- **开始归档整部番**：每部 ≈ 5 GB，10 部就 50 GB —— 所以默认用引用模式

判断就很清楚了：**程序本身 20 MB，可以忽略；空间全看你要不要把视频搬进库里**。

### 代码规模

Rust 约 3000 行（服务、数据库、AniList 对接、媒体流），前端约 4000 行（搜索、封面墙、详情、播放器）。P0 阶段实际只需要其中三分之一。

### 过程中踩的坑（备查）

1. **rsproxy 的 rustup-init 链接返回 504**，改用 USTC 镜像才下下来。
2. **rustup-init 必须保持原文件名**，改成 `r1.exe` 会被当成 proxy，报 `unknown proxy name`。
3. 机器原本没有 Rust / MSVC，本次装了：rustup（USTC 镜像，minimal profile）+ VS Build Tools 2022（VCTools + Windows SDK 10.0.26100）。首次依赖编译约 1 分钟。
4. **搜索下拉曾一直显示"没找到"**：`useMemo` 只依赖 `q`，索引异步加载完不会重算。依赖里补上 `indexReady / indexSize` 后修复。
5. 剧场版不显示"集数"（AniList 里 movie 的 episodes 常为 1）。
6. 索引里给无中文名的条目回填日文名，避免出现空白行。

## 附录 B：P1 已落地（2026-11-23）

### 详情抽屉

点封面卡片从右侧滑出，宽度 460，Esc 或点遮罩关闭：

| 区块 | 行为 |
|---|---|
| 状态 | 想看 / 在看 / 看完 / 搁置 / 弃番 五段切换；切到「看完」自动补当天日期，切走则清空 |
| 评分 | 1–10 十个格子，点同一个可取消 |
| 进度 | 加减步进 + 进度条；到达总集数自动转「看完」并补日期 |
| 看完日期 | 原生 date 输入 |
| 短评 | 输入后 600ms 防抖自动保存 |
| 简介 | 折叠区，无嵌套滚动 |
| 删除 | 二次确认后移除 |

题材标签做了中英映射（Action → 动作 等 18 个）。

### 列表

- 筛选：全部 / 在看 / 看完 / 想看 / 搁置 / 弃番，每个带实时计数
- 排序：最近加入 / 评分最高 / 年份最新 / 按标题
- 卡片副标题会显示评分；在看状态显示 `已看/总数` 而不是总集数
- 支持 `?work=12` 深链直接打开某部详情

### 服务端配合

- `PATCH` 时若状态变 `done` 且无日期，用 `date('now','localtime')` 兜底（不只依赖前端）

| 接口 | 说明 |
|---|---|
| `GET /api/works/:id/media` | 素材列表 |

### 前端

- 详情抽屉底部「素材」网格，3 列，视频带 `▶ 时长` 角标，引用模式带「引用」小标

### 两个关键决定

1. **缩略图和视频首帧都在浏览器 canvas 里生成**，不引 `image` crate、不装 ffmpeg。前端生成 480px JPEG 缩略图 / 640px 首帧一并上传，服务端只存文件。

### 实测

### 踩的坑

1. **改了路由没重编 devserver**，`/media/import` 一直返回 405，白查了一会儿。改后端一定要重启。
2. **灯箱被抽屉的层叠上下文压住**：`MediaGallery` 在 `.drawer` 里，fixed 定位的灯箱受祖先影响。改用 `createPortal` 挂到 `document.body` 解决。
3. **headless 截图整体发白**：CSS 入场动画被虚拟时间冻在起始帧（opacity≈0）。加 `prefers-reduced-motion` 归零动画时长，既是无障碍改进，也让截图能拿到动画结束态。
4. 拖拽事件需要 `core:default` 权限，补了 `src-tauri/capabilities/default.json`，并把窗口 label 显式设为 `main`。

### 已知限制

- 视频首帧只能由浏览器解出来的格式生成（mp4/webm 可以，mkv/avi 大概率不行），这类视频在网格里显示为「▶」占位，仍可点开播放（取决于 WebView2 解码能力）。
- 引用模式的文件如果被移动或删除，列表会标「文件丢失」，需要重新导入。

### 待办（P3）

## 附录 E：P3 手机访问（2026-11-23）

### 架构变化

之前前端只有两条来源：开发时 vite、打包时 `tauri://`。手机两条都用不了，所以：

- `rust-embed` 把 `dist/` 编进二进制，axum 用 `fallback(spa)` 直接端出静态文件，未知路径回退 `index.html`
- 服务从 `127.0.0.1` 改为绑 `0.0.0.0`，手机走 http://<电脑IP>:8787
- 桌面端不受影响：仍从 `tauri://` 加载、请求打到 `127.0.0.1:8787`，且本机访问免口令

### 鉴权

| 项 | 做法 |
|---|---|
| 本机访问 | 按 `ConnectInfo` 判断 loopback，直接放行（桌面应用无需登录） |
| 局域网访问 | 必须有 `cn_token` cookie，否则 `/api/*` 返回 401 |
| 口令 | 40 位随机串，首次启动写进 `settings` 表，重启不变 |
| 配对码 | 6 位数字，内存态，5 分钟有效，**用一次即作废** |
| 扫码 | `GET /pair?c=code` 校验通过后种 cookie 并 302 到 `/` |
| 二维码 | 服务端用 `qrcode` crate 生成 SVG，`/api/pair` 返回；该接口只对本机开放 |

静态资源不设限（否则登录页的 CSS 都加载不了），只有 `/api/*` 需要凭证。

### 界面

- 顶栏右上角「手机访问」→ 弹窗显示二维码、地址、配对码，可复制、可换码
- `?pair=1` 可直接打开弹窗（调试/深链用）
- 移动端 CSS：两列封面、筛选标签可横滑、抽屉全宽、灯箱去圆角

### 两个坑

1. **rust-embed 是编译期内嵌**，改了前端不重新编译，端出来的还是旧页面。`build.rs` 里加了 `cargo:rerun-if-changed=../dist` 才治本。
2. **Edge headless 的窗口宽度会被限制在 ~504px**，我用 `--window-size=390` 截的所有「手机图」其实都是 504 视口左边裁 390，看起来像布局溢出，实际是截图假象。判断依据：页面自己报 `innerWidth=504`。要看真机宽度得用 `--force-device-scale-factor` 配合，或者干脆用 520px 验证。

### 实测

- 本机 `/` `/api/works` 200
- 局域网地址 `/api/works` 401（未配对）
- 局域网地址 `/` 200（静态页可用）
- 扫码链接 → 303 + `Set-Cookie` → 带 cookie 请求 API 200 → 同码二次使用 403
- 独立版 exe 启动后 `/api/pair` 正常返回二维码 SVG

### 已知限制

- 局域网地址取的是**默认路由网卡**的 IP。这台机器以太网直连拿到的是公网地址（180.117.58.144），手机能否连通取决于是否同一网络 + 防火墙放行 8787。默认路由被 VPN 抢走时会退回到 `ipconfig` 里的 192.168 地址。
- 首次启动可能弹 Windows 防火墙授权，需要勾「专用网络」。
- 手机端暂不支持上传素材（只读浏览 + 播放）。

## 附录 I：修图标（2026-11-23）

### 症状

独立版 exe 的图标显示不对（资源管理器/桌面是默认或空白图标），但 `icons/icon.ico` 打开看是正常的头像。

### 排查过程

1. 对比 `icons/icon.ico` 的 7 帧 → 全是同一张头像，文件内容没问题
2. 在 exe 里搜各帧的像素数据 → 7/7 命中，**但这个结论是假的**：`public/icon.png` 会经 rust-embed 打进 dist 再嵌进 exe，同样的字节自然能找到
3. 手写 PE 资源目录解析 → 7 个 `RT_ICON` + 1 个 `RT_GROUP_ICON`（104 字节 = 6 + 14×7，正好对应 7 帧），确认图标资源确实在
4. 真正的问题在帧的**编码**：`icon.ico` 里 7 帧全是 PNG

### 根因

Pillow 13 的 `Image.save("x.ico", sizes=[...])` 默认 `bitmap_format` 不是 `"bmp"`，会把**每一帧**都写成 PNG。而 Windows 只对 256×256 这一档较稳定地支持 PNG 帧，小尺寸 PNG 帧常被当成无效，shell 于是退回默认图标。

### 修法

不再用 Pillow 存 ICO，改为自己组装容器（`scripts/make-icons.py`）：

- ≤128：32bpp BMP 帧（BITMAPINFOHEADER + 自下而上 BGRA + 1bpp 全零掩码）
- 256：PNG 帧（体积从 262 KB 降到 94 KB）

重新生成后 7 帧变成 `BMP×6 + PNG×1`，总大小 196 KB。重新编译后在新 exe 里能搜到 32×32 / 16×16 的 BMP 帧头，确认已嵌入。

最后重建桌面快捷方式并跑 `ie4uinit.exe -show` 刷新图标缓存——同一路径反复覆盖 exe，shell 会缓存旧图标。

### 教训

「在二进制里搜到图标字节」不能证明图标资源正确，dist 里的同名图片会误导判断。要验图标得看资源表，或者直接查 ICO 每一帧的编码。

## 附录 J：独立版「打不开」的真正原因（2026-11-23）

### 症状

桌面快捷方式双击后打不开。我这边用 `os.startfile` 启动却能在 0.6 秒内弹出窗口——看起来完全正常。

### 定位

复现「已有实例在跑时再双击」的场景，发现第二个窗口显示的是 WebView2 的 **「无法访问此页面 / localhost 拒绝连接」**，不是应用界面。

这说明这个 exe 在加载 `localhost:5173`（vite 开发地址），而本机并没有跑 vite。

### 根因

**用 `cargo build --release` 直接编译时，tauri-build 仍然按 dev 模式处理**（编译命令行里能看到 `--cfg dev`），窗口 URL 被定成 `devUrl`。只有走 `npm run app:build`（tauri CLI）才会按生产模式编译，加载内嵌资源。

我在 13:46（补标签/导出那轮）和 14:38（修图标那轮）两次为了省事直接跑了 `cargo build --release`，结果这两版 exe 都是「开发模式」的——双击就弹 localhost 拒绝连接，看起来像打不开。

### 修法

```
npm run app:build      # 唯一的打包入口，不要用 cargo build --release
```

即便最后 NSIS 打包那步因为下载 nsis_tauri_utils.dll 失败，**exe 在打包之前就已经生成好了**，可以照常使用。

### 验证方式

静态检查靠不住：`localhost:5173` 在配置里本来就有，两种包都能搜到。唯一可靠的验证是**在没有 vite 的情况下启动，看窗口显示什么**：

- 正确 → 封面墙、作品卡片
- 错误 → 「无法访问此页面」

### 教训

`cargo build --release` ≠ 生产包。这个坑没有任何报错提示，编译成功、程序能跑、窗口能弹，只是内容全错。

## 附录 K：Wallpaper Engine 壁纸当背景（2026-11-23）

### 先做了可行性勘查

扫了本机 `E:/SteamLibrary/steamapps/workshop/content/431960`（187 个创意工坊壁纸，共 11 GB）：

| 类型 | 数量 | 能否用 | 原因 |
|---|---|---|---|
| video（mp4） | 45 | ✅ | 普通 mp4，能播、能截帧 |
| scene（scene.pkg） | 130 | ❌ | `scene.pkg` + 自定义 shader，只有 WE 自己的引擎渲染得出来 |
| web（index.html） | 5 | ❌ | 依赖 `wallpaperProperty` 等 WE API，且等于执行任意本地脚本 |

体积：中位 21 MB，最大 1.5 GB。所以**不能复制**，只记路径。

### 实现

后端（`server.rs`）：

- `steam_roots()` 先读注册表 `HKCU\Software\Valve\Steam`，再补几个常见安装路径
- `library_roots()` 解析各库的 `steamapps/libraryfolders.vdf`（手工按 `"path"` 行切分，不引 VDF 库）
- `scan_wallpapers()` 遍历每个库的 `431960/*/project.json`，解析 `type / title / file / preview / tags`，多库按工坊 id 去重
- 扫描结果缓存在 `AppState.wallpapers`，`?refresh=1` 强制重扫
- 接口：`GET /api/wallpapers`、`GET /api/wallpapers/:id/preview`、`GET /api/wallpapers/:id/video`（ServeFile，带 Range）、`GET/PATCH /api/wallpaper`
- 只按工坊 id 反查路径，不暴露任意文件读取

前端：

- 顶栏「背景」按钮 → 弹窗网格（16:9 预览 + 标题 + 体积 + 标签），点选即套用并落库
- 背景层是 `<video autoplay muted loop>` 铺满 `position: fixed; z-index: -1`，上面盖一层 `rgba(251,250,247,.8)` + `blur(3px)` 的米白薄纱，保证正文可读
- 有壁纸时给 `<html>` 加 `has-wallpaper`，把 html/body 背景改透明，否则视频被页面底色挡住
- `poster` 指向该壁纸的预览图：加载中或解码失败时不会出现一片灰
- `visibilitychange` 时暂停播放，窗口在后台不空转解码

### 踩的坑

壁纸网格第一版被压成一条条细片：`.wp-grid` 在 flex 竖排的弹窗里，`align-content: stretch` 把 45 个项目均匀分配了容器高度，行高被压到 30px，图片再被 `overflow: hidden` 裁掉。修法是 `grid-auto-rows: max-content` + `align-content: start` + `flex: 1 1 auto; min-height: 0`。

### 未验证的部分

**H.264 播放**：headless Edge 没有 H.264 解码器，截图里视频是黑帧（正好用来看薄纱效果）。真机 WebView2 走 Media Foundation 解码，理论上没问题，但需要用户实际看一眼。

### 已知限制

- 场景壁纸（占 130/185）用不了，这是 WE 的私有格式，除非实现整套渲染器
- 4K60 视频壁纸常驻播放比较耗电，笔记本上建议选小体积的
- Steam 库移动/卸载后路径会失效，重新扫描即可

## 附录 L：按 dsh-plugin-wallpaper 重做背景（2026-11-23）

参考了 DeepSeek Harness 的 `dsh-plugin-wallpaper`（william-godric-han/dsh-plugin-wallpaper）。它的做法比第一版完整：图片+视频、薄纱、模糊 0–24px、填充模式、临时开关、预设渐变。

### 吸收了什么

| 能力 | 第一版 | 现在 |
|---|---|---|
| 素材 | 只有视频壁纸 | 视频 + **场景壁纸的预览图（静态）** |
| 薄纱 | 写死 0.8 | 滑杆 0–100%，即时生效 |
| 模糊 | 写死 3px | 滑杆 0–24px，模糊时画面放大 1.04 倍盖住边缘 |
| 填充 | 只有 cover | cover / contain |
| 临时开关 | 没有，只能"关闭" | `enabled` 与选中分离，关掉但记住 |
| 状态指示 | 无 | 顶栏「背景」按钮上的红点 |

**最有价值的是静态图**：130 个场景壁纸虽然没有可播放的视频，但每个都有 `preview.jpg`。允许拿它当静态背景，可用率从 45/185 变成 **185/185**。

### 数据模型

`settings.wallpaper_config` 存一段 JSON：

```json
{ "id": "2862394317", "enabled": true, "veil": 0.55, "blur": 8, "fit": "contain" }
```

`PATCH /api/wallpaper` 只改传入的字段，全部 `clamp` 到合法区间。兼容早期只存 `wallpaper = id` 的格式（读到就迁移，随后删掉旧字段）。

### 与参考实现的差异

- 它把图片存 IndexedDB，纯前端；我们是**服务端存配置 + 按工坊 id 反查路径**，所以手机端访问也能看到同一个背景。
- 它支持任意本地图片；我们暂时只从 WE 库取（没有文件选择器插件，硬加要引 tauri-plugin-dialog）。
- 它的"预设渐变"没做——你有 185 张现成的壁纸，渐变没什么意义。

### 踩的坑

改 `[profile.dev] debug = 1` 导致所有依赖缓存失效，触发了一次 **6 分 36 秒的全量重编译**。期间：

- `cargo build ... | tail` 因为管道缓冲，几分钟没有任何输出，被工具当成长时间静默任务杀掉（SIGTERM）
- 同时 `Edit` 工具报 `sandbox-center request timed out`——磁盘被编译占满

教训：**长编译不要接管道**，直接重定向到日志文件、后台跑、再轮询日志。

### 验证

用发布版（`app/CartoonNotebook.exe`）走 `CARTOON_DATA_DIR=.testdata` 跑接口：选视频壁纸、改薄纱/模糊/填充、临时关闭、切场景壁纸、清空，返回的结构都正确。截图直接打 `http://127.0.0.1:8787/`，即生产构建的内置页面。

**H.264 播放仍未实机验证**（headless Edge 没解码器），但静态壁纸和 poster 兜底路径已经验证。

## 附录 M：播放续播、素材重定位与冒烟测试（2026-11-23）

### 功能

**播放续播**：`media` 表加 `position REAL`（老库自动 ALTER）。灯箱视频打开时若上次位置 > 3 秒且不在片尾附近，自动跳过去；播放中每 3 秒落库一次，关灯箱再落一次；缩略图底部有细进度条。

**素材重定位**：引用模式的素材文件被移动后，灯箱里出现「重新定位」按钮，用 Tauri 的 dialog 插件选新文件（为此加了 `tauri-plugin-dialog` + `dialog:default` 权限）。`PATCH /api/media/:id` 新增 `path`（只允许引用模式，会校验文件存在并更新体积/类型/missing）和 `position` 字段。

### 冒烟测试（工程欠账）

`scripts/smoke.py`（`npm run smoke`）：

- 自动起服务：临时数据目录 + 独立端口 17878（可用 `SMOKE_PORT` 换），跑完清理

## 附录 N：备份恢复、标签管理、窗口记忆（2026-11-23）

### 备份恢复（补上另一半）

`POST /api/restore`：接收导出的 zip（multipart 流式写盘，几个 GB 也不会撑爆内存），校验含 `manifest.json` + `library.db`，按白名单（manifest.json / library.db / covers/ / media/，拒绝 `..`）解压到 `data/.restore-pending/`。

前端在备份弹窗下半部分加了恢复入口；上传成功后提示"重启应用后生效"。
